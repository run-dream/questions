以下是根据课程 "AI Coding for Real Engineers" (Cohort 004, Lesson 26) 中关于 Claude Code 上下文压缩（Auto-Compact Buffer / /compact 命令）与上下文管理策略的系统性总结。

---

### 🎯 **一、什么是 Auto-Compact Buffer？**

Claude Code 在上下文窗口末尾预留了一个 **自动压缩缓冲区**：

| **属性** | **说明** |
|----------|---------|
| **大小** | ~33K tokens（约占 200K 窗口的 16.5%） |
| **位置** | 上下文窗口的最末尾 |
| **作用** | 当上下文填满至该缓冲区边界时，自动触发压缩（Compact） |
| **使用方式** | LLM 本身不会读取该缓冲区中的内容 — 它只是一个预留的停止间隙（Stopgap / Reserve Space） |

**工作流程**：
1. 上下文不断填充，逐渐接近 200K 上限
2. 当剩余空间触及 ~33K 的 Auto-Compact Buffer 边界时
3. Claude Code 自动触发 **/compact** 操作
4. 将当前大量对话历史压缩为一份 Markdown 摘要

---

### **二、/compact 命令是如何工作的？**

#### **基本用法**
```
/compact
→ （可选）输入自定义的 summarization instructions
→ LLM 开始压缩当前对话
→ 上下文从高位（如 49%）降至 ~12%（约 23K tokens）
```

#### **压缩过程中发生了什么？**

| **动作** | **说明** |
|----------|---------|
| **压缩对象** | Tool calls、File reads/writes、Q&A 等完整的对话历史 |
| **压缩方式** | LLM 将原始内容重新组织为一篇 Markdown 格式的总结 |
| **压缩效果** | 例如 49% 上下文占用 → 压缩至 12%（约 23K tokens） |
| **原始记录** | 完整的对话历史会被保存到文件中备查 |

#### **压缩后会保留什么？**
- **关键代码片段**（Key code snippets）— 项目中修改的核心逻辑
- **所有用户消息**（ALL user messages）— 保留用户意图（Intent）
- **文件引用**（File references）— 仅保留路径（Paths），不保留完整文件内容
- **待办任务**（Pending tasks）— 尚未完成的工作

#### **自定义压缩指令（Summarization Instructions）**

在执行 `/compact` 时，可以额外输入一段指令，告诉 LLM **为什么要压缩**。这会影响摘要的侧重点：

> 示例：执行 `/compact`，然后输入 *"I want to do QA on this feature"*
> → 生成的摘要会更侧重于：已实现的功能、待测试的边界条件、潜在风险点

---

### 🔻 **三、什么是 Sediment Problem（沉积问题）？**

这是 **/compact 模式的最大陷阱**。每次压缩都会在上下文中留下一层"沉积层"（Sediment Layer），随着多次压缩不断累积：

#### **图示：三次压缩的演变**

| **阶段** | **上下文内容** | **信息保真度** |
|----------|---------------|---------------|
| Session 1 | 原始对话 → 首次压缩 | Layer 1：摘要版本 |
| Session 2 | Layer 1 摘要 + 新对话 → 再次压缩 | Layer 2：对摘要的摘要 |
| Session 3 | Layer 2 摘要 + 新对话 → 第三次压缩 | Layer 3：极度抽象版本 |

#### **核心问题：每次压缩都是有损压缩（Lossy Compression）**

- 第一次压缩：用 LLM 的摘要代替原始信息 — **已丢失部分细节**
- 第二次压缩：对摘要再进行摘要 — **丢失了更多细节**
- 第三次压缩：多层"摘要的摘要"堆叠 — **行为不可预测（Unpredictable Behavior）**

> **关键洞察**：你保留下来的不是原始信息（Raw Information），而是一个 LLM 对它的解读（LLM's Summary）。叠加压缩就是叠加信息损失。

### 🆚 **四、/compact、/clear 与 Handoff 的对比**

| **维度** | **/clear** | **/compact** | **Handoff** |
|----------|-----------|-------------|------------|
| **上下文占用** | 重置为 0 | 压缩至 ~12% | 独立新窗口 |
| **历史记录** | 全部丢失 | 摘要形式保留 | 摘要 + 文件链接 |
| **是否需要重新探索** | 是（需要额外 tokens） | 否（摘要中已包含上下文） | 否（交接文档已包含） |
| **沉积风险（Sediment Risk）** | 无 | 有（每次压缩增加一层） | 无 |
| **推荐使用场景** | 常规任务切换 | 调试、实现完成后追加反馈 | 分离子任务、深挖子话题、双向交互 |

### 📋 **五、讲师准则（Instructor's Guidelines）**

#### **核心理念**
> **目标：永远不需要 /compact。** 设计工作流，让每次 Agent 调用都是独立的 Clean Context，Agent 可以在后台（AFK）自行工作。

#### **最大限制**
> **每次会话中最多只做 1 次 /compact，绝不多次。**

#### **✅ 好的使用场景**
1. **功能实现刚刚完成，想快速追加反馈** — 不需要重新探索所有上下文
2. **调试一个复杂 bug，尝试了很多方案** — 不想丢失这些试错历史

#### **❌ 坏的使用场景**
- **反复使用 /compact 来无限延长同一轮对话** — 这是典型的反模式（Anti-pattern）

#### **讲师的原话**
> *"When I do compact, I usually feel bad about it afterwards."*
> — 讲师的直觉判断：使用 /compact 通常意味着设计上出了问题

#### **社区争议**
- 大多数社区成员认同"Anti-pattern"的观点
- 但也有一些知名人士持不同意见（少数派）

### 🔧 **六、上下文管理策略对比**

| **策略** | **操作方式** | **优点** | **风险** |
|----------|-------------|---------|---------|
| **Clean Context 策略（推荐）** | 每完成一个任务就 `/clear`，重新开始新会话 | 行为可预测（Predictable），始终保持在 Smart Zone | 需要消耗 tokens 重新建立上下文 |
| **Compact 策略** | 每次填满后 `/compact`，继续当前会话 | 不需要重新探索，节省时间 | 沉积层累积（Sediment Accumulation），最终进入 Dumb Zone |
| **Handoff 策略** | 写 Markdown 交接文档 → 新会话读取 | 无沉积物，可双向交接，分离子任务 | 需要手动撰写交接文档 |

#### **Clean Context 的核心优势**
- 每次都在 **Smart Zone** 内工作
- 没有沉积层，不会产生"摘要的摘要"
- Agent 可以 **AFK（Away From Keyboard）** 自主工作 — 启动后不需要人盯着

### 🤝 **七、Handoff — 会话交接（Lesson 27）**

Handoff 是除了 `/clear` 和 `/compact` 之外的**第三种上下文管理方案**。

#### **问题场景**
在一个会话中处理主任务时，发现了 Bug 或损坏的测试。可选方案：
- 在当前会话中修复 → 消耗大量 tokens，可能超出 Smart Zone
- `/clear` → 丢失主任务的所有上下文
- `/compact` → 存在沉积物风险

**Handoff 的解决方案**：撰写一份 Markdown 交接文档，总结当前对话，保存到临时目录，然后**启动一个新的会话**读取该文档。因为是全新的上下文窗口，所以没有沉积物风险。

#### **Compact vs Handoff 对比**

| | **Compact** | **Handoff** |
|---|---|---|
| **方式** | 同一会话内压缩 | 写文件 → 新会话读取 |
| **沉积物** | 有（残留压缩层） | 无（独立会话） |
| **方向** | 单向（只能缩小） | 双向（可来回交接） |
| **用途** | 快速追加反馈 | 分离子任务、深挖子话题 |

#### **Handoff Skill 的核心要点**
- 保存到临时目录（`mktemp -t handoff.XXXXXX.md`），不污染项目
- 建议下一个会话用什么 Skill（如继续 Grill Me）
- 不重复已有工件内容——只放链接
- 根据下一阶段目标定制文档内容

#### **三种典型使用场景**

1. **中途发现 Bug**：主任务 → Handoff → 新会话修 Bug → 修完回来
2. **Grill Me 子话题深挖**：Grill Me → 某块太复杂 → Handoff → 新会话专门 Grill → 可能还建原型、做研究 → Handoff 回来浓缩为小结
3. **跑进 Dumb Zone**：不用 compact（有沉积物）→ Handoff 到新会话 → 干净上下文 + 累积的关键决策

#### **核心理念：扩展再收缩（Expand & Contract）**

需要时可以炸开成多个大会话，每完成一部分就浓缩成交接文档，组装回来。

### 📊 **八、三种上下文管理方式完整对比**

| **维度** | **/clear** | **/compact** | **Handoff** |
|----------|-----------|-------------|------------|
| **上下文占用** | 归零 | 压缩到 ~12% | 独立新窗口 |
| **历史保留** | 全丢 | 摘要保留 | 摘要 + 文件链接 |
| **沉积物** | 无 | 有 | 无 |
| **需重新探索** | 是 | 否 | 否（交接文档已包含） |
| **适用场景** | 正常流程 | 调试/紧急追加反馈 | 分离子任务/深挖/双向交互 |
