以下是根据课程 "AI Coding for Real Engineers" (Cohort 004, Lessons 36-37) 中关于 PRD + Plan 大任务跨上下文窗口拆分与 2PRD Skill 的系统性总结。

---

### 🧠 **一、问题背景：大任务溢出上下文窗口**

小功能可以在单个 Smart Zone 内完成。但大任务（如重构、analytics dashboard）会溢出上下文窗口。

**解决方案**：和开发者几十年一样——拆小任务。但关键是要有**两张文档**来指导拆分：

| **文档** | **作用** | **视角** | **类比** |
|----------|---------|----------|---------|
| **PRD (Product Requirements Document)** | 描述"目的地"——你要构建什么 | 用户视角 | 建筑设计蓝图 |
| **Plan (Implementation Plan)** | 描述"旅程"——分几个 Phase，每个 Phase 做什么 | 开发者视角 | 施工进度表 |

> **PRD 也是你作为人类施加品味（impose your taste）的地方**——明确你究竟想要什么，而不是让 AI 替你决定。

---

### 🔄 **二、多会话工作流程**

```
Session 1:    Grill Me → 访谈需求 → 达成共识
                  │
Session 1-2:  /2PRD  → 生成 PRD 文件（目的地文档）
                  │
Session 2-3:  基于 PRD 创建 Plan（分阶段计划）
                  │
Session 4~N:  执行各 Phase

    每 Phase 的 Prompt = "实现 Phase N" + PRD + 完整 Plan
```

#### **为什么每次都要传完整 Plan？**

让 AI 看到全貌，知道 Phase 3 才做的不会在 Phase 2 提前做，避免各阶段互相踩脚。例如：

- Phase 2 做数据采集
- Phase 3 做数据可视化
- 如果不传完整 Plan，Phase 2 的 AI 可能自作主张开始画图，导致代码冲突或重复工作

| **做法** | **结果** |
|----------|---------|
| 只传当前 Phase | AI 可能超前实现后面 Phase 的内容，造成冲突 |
| 传完整 Plan | AI 知道边界，只做当前 Phase 该做的事 |

---

### 📋 **三、2PRD Skill（Lesson 37）**

将 Grill Me 对话产物转成 PRD 文档的 Skill。

#### **两步流程**

1. **Explore repo** — 了解代码库现状（文件结构、现有功能）
2. **使用模板写 PRD** — 保存到本地文件

#### **PRD 模板结构**

```
1. Problem Statement  — 用户面临什么问题（从用户视角描述）
2. Solution           — 解决方案（从用户视角描述）
3. User Stories       — 编号列表的用户故事
```

> 讲师表示模板可以争论和迭代，但这**是目前的最佳实践**。

### 🏗️ **四、练习任务：Instructor Analytics Dashboard**

#### **现状**
- 当前教师 dashboard 功能太弱

#### **目标新功能**
- 学生数量统计
- 收入统计
- 完成率分析
- 测验得分率分析
- Drop-off 分析（学生在哪一步退出）

#### **为什么适合这个工作流**
这个任务"庞大和多变"——功能边界不清晰，需求可能随讨论变化，正适合 Grill Me + PRD 工作流来收敛需求。

#### **操作流程**

| **步骤** | **操作** | **产出** |
|----------|---------|---------|
| 1 | `/grill-me` | 访谈记录，收敛需求 |
| 2 | 达成共识后 → `/2PRD` | PRD 文档 |
| 3 | 审查 PRD 是否捕获 shared design concept | 修改后的 PRD |
| 4 | Commit PRD（仅文档，不实现） | 版本化的 PRD 文件 |

> **关键原则**：此阶段只产出文档，不实现任何代码。PRD 确认后再创建 Plan，Plan 确认后再开始实现。

### 🧩 **五、PRD 与 Plan 的协作关系**

```
PRD（What）                  Plan（How）
─────────────────           ─────────────────
Problem Statement            Phase 1: 数据模型 + API
Solution                     Phase 2: 前端组件
User Stories                 Phase 3: 可视化 + 报表
                             Phase 4: 权限 + 部署
```

| **维度** | **PRD** | **Plan** |
|----------|---------|---------|
| **回答的问题** | 构建什么？ | 怎么构建？ |
| **受众** | 产品/用户 | 开发者/AI |
| **变更频率** | 低（需求确定后基本不变） | 中（实现过程中可调整） |
| **责任方** | 人类主导（impose taste） | 人类 + AI 协作 |
| **产物形式** | 用户故事 + 需求描述 | Phase 列表 + 技术细节 |

---

### 💡 **六、关键原则总结**

1. **先文档，后代码** — PRD 确认前不写一行代码
2. **人类 impose taste** — 不要让 AI 替你决定产品方向
3. **传完整 Plan** — 每个 Phase 执行时都带上完整 Plan，避免各阶段冲突
4. **Grill Me 是入口** — 大任务从 `/grill-me` 开始，不要跳过需求访谈
5. **PRD 模板可迭代** — 当前三个部分（Problem Statement + Solution + User Stories）是最佳实践，但可根据项目调整

### ⚖️ **七、2PRD 与其他文档化方法的对比**

在 AI 编码工作流中，文档化需求有多种思路。2PRD 只是其中一种，它的定位在"形式化 Spec"和"自由头脑风暴"之间。

**对比表：**

| 维度 | 2PRD（课程方式） | 形式化 Spec（如 OpenSpec 思路） | 自由头脑风暴（Brainstorm 思路） |
|---|---|---|---|
| 输入 | Grill Me 对话 | 结构化字段（标题/范围/验收标准/边缘情况） | 任意自由对话 |
| 输出 | 3 段式（Problem / Solution / User Stories） | 结构化文档，可能含技术约束、API 签名 | 无固定格式，散点想法 |
| AI 理解难度 | 低 | 中（字段越多越需要 AI 理解上下文） | 高（散乱信息难以转化为执行指令） |
| 人力成本 | 低（Grill Me 访谈即产出） | 高（需要人工填写很多字段） | 极低（随口说） |
| 适合场景 | 单人+AI 快速迭代 | 团队协作、需要审查流程 | 探索阶段、还不确定做什么 |
| 最大弱点 | 模板太简单，复杂项目可能不够 | 太重，小功能没必要；模板容易过时 | 太散，AI 容易误解或遗漏 |

**核心权衡：** 2PRD 的本质是用最简单的模板把 Grill Me 的共识固定下来——追求"刚好够用"。如果项目规模更大需要更多结构性，往形式化 Spec 方向走；如果还在探索阶段不确定需求，Brainstorm 流更自然。

**选择建议：**
- 单人+AI 快速迭代 → 2PRD（轻量够用）
- 团队多人协作、需要正式评审 → 形式化 Spec
- 需求完全不明确、还在探索 → Brainstorm → 再走向 2PRD 或 Spec
- 大型项目 → 2PRD 作为起点 → 拆分到各子模块再用更详细的 Spec
