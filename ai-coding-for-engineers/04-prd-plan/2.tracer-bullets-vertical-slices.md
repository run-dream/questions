### 🎯 **一、Tracer Bullets 的概念起源**

#### **来自《The Pragmatic Programmer》**
Tracer Bullets（曳光弹）概念源自 Andy Hunt 和 Dave Thomas 的经典著作 **《The Pragmatic Programmer》**。

| **概念** | **来源** | **核心思想** |
|----------|---------|-------------|
| Tracer Bullet | The Pragmatic Programmer | 用实弹快速验证系统全链路，而非在理论层面规划所有细节 |
| Prototype（原型） | 传统软件工程 | 做出来就是为了扔掉（Throwaway），只为验证可行性 |
| **关键区别** | — | Tracer Bullet 的代码**不扔掉**，它随着项目演进持续生长 |

#### **WWII 防空炮隐喻**

Tracer Bullets 的命名来自二战时期的防空炮：

1. **传统方式**：在纸面上计算弹道、风速、目标速度等所有参数，计算出"完美"的射击方案再开火
2. **曳光弹方式**：装填实弹（含曳光剂），直接开火，观察弹道轨迹，**实时修正**下一发
3. **关键洞察**：在真实环境中比理论计算更有效

> **映射到软件开发**：不要花几周时间设计完美的架构图，先写一个贯穿全栈的端到端功能，让代码告诉你架构该怎么调整。

### 🔫 **二、为什么 LLM 默认使用 Horizontal Thinking（水平思维）？**

#### **LLM 的天生倾向**

当要求 LLM 为某个功能制定计划时，默认输出是**水平分层**的：

```
Naive Plan（LLM 默认行为）:
  Phase 1: 创建 Service 层 — 实现所有业务逻辑
  Phase 2: 创建 Component 层 — 封装所有 UI 组件
  Phase 3: 创建 Route 配置 — 添加路由和导航
  Phase 4: 创建 Admin 面板 — 管理员功能界面

→ 每个 Phase 只做一层，到最后才能看到完整功能
```

| **维度** | **LLM 默认行为** | **问题** |
|----------|-----------------|---------|
| **思维方式** | 水平分层（Horizontal Layers） | 不符合用户"端到端可用"的期望 |
| **计划粒度** | 按技术层划分 Phase | 各 Phase 之间存在隐性依赖 |
| **验证时机** | 最后 Phase 才能验证 | 问题到最后才暴露 |
| **变更成本** | 高（早期决策固化） | 后期发现架构问题需要大面积返工 |

#### **为什么 LLM 会这样？**
- LLM 训练数据中的软件工程教材大多强调"分层架构"
- 分层架构在理论上"干净"，但实践中各层之间的假设可能不匹配
- LLM 倾向于模仿"教科书式"的规划方式

#### **解决方法：在 prompt 中加入"tracer bullets"两词**

> **实验发现**：仅仅在 prompt 中加入 "tracer bullets" 这两个词，LLM 的输出计划就从水平分层变成了**垂直切片**。
>
> 这两个词建立了 shared design concept，改变了 LLM 对"什么是好的计划"的理解。

### 🥩 **三、Vertical Slices（垂直切片）的核心思想**

#### **什么是 Vertical Slice？**

| **水平分层（Horizontal Layers）** | **垂直切片（Vertical Slices）** |
|-----------------------------------|-------------------------------|
| Phase 1: 数据模型 | Phase 1: 实现 User Story #1（贯穿数据+API+UI） |
| Phase 2: API 层 | Phase 2: 实现 User Story #2（贯穿数据+API+UI） |
| Phase 3: UI 组件 | Phase 3: 实现 User Story #3（贯穿数据+API+UI） |
| Phase 4: 集成测试 | Phase 4: 实现 User Story #4（贯穿数据+API+UI） |
| 只有 Phase 4 完成才能看到效果 | **每个 Phase 结束时功能完整可用** |

**Vertical Slice 的定义**：一个 Phase 的实现应该**贯穿所有技术层**（数据模型 → API → 业务逻辑 → UI），实现一个完整的端到端功能。

#### **为什么 Vertical Slices 更好？**

| **优势** | **说明** |
|----------|---------|
| **早期验证** | Phase 1 完成就能看到一个完整功能在运行 |
| **风险暴露** | 整合问题（Integration Issues）在 Phase 1 就被发现 |
| **渐进交付** | 每个 Phase 都有价值可交付 |
| **变更灵活** | Phase 2 发现 Phase 1 的架构问题，立即调整 |
| **用户可见** | Stakeholders 可以在早期看到真实进度 |

#### **讲师原话**
> *"Each phase should touch all layers. You should build a complete feature end-to-end, not build all the services first and then all the UIs."*

### 📋 **四、Tracer Bullet Plan 的三要素**

一个 Tracer Bullet Plan 必须包含以下三个元素：

| **要素** | **说明** | **为什么重要** |
|----------|---------|---------------|
| **1. Vertical Slices（垂直切片）** | 每个 Phase 贯穿所有技术层 | 确保每个 Phase 交付完整功能 |
| **2. User Story 引用** | 每个 Phase 明确引用 PRD 中的 User Story 编号 | 确保每个 Phase 都有明确的产品价值；让 AI 知道在做什么 |
| **3. Durable Decisions（持久决策）** | 只记录那些一旦做错就代价高昂的决策 | 避免伪代码式的"计划垃圾" |

---

### 🏛️ **五、Durable Decisions（持久决策）详解**

#### **什么是 Durable Decisions？**

Durable Decisions 是那些**一旦做错，需要大量返工才能纠正**的技术决策。

| **属于 Durable Decisions** | **不属于 Durable Decisions** |
|---------------------------|------------------------------|
| 项目整体技术栈（React vs Vue） | 具体的函数名称 |
| 数据库选型（PostgreSQL vs MongoDB） | 当前 Phase 的函数签名 |
| 核心数据模型设计 | 变量命名约定 |
| API 设计范式（REST vs GraphQL） | 临时文件路径 |
| 状态管理模式 | 当前 sprint 的详细实现步骤 |

#### **核心原则：Don't Plan What You Can't Plan**

> **"Don't plan what you can't plan."** — 讲师的核心理念

| **可以计划的** | **不应该计划（或者计划了也没用）的** |
|---------------|-------------------------------------|
| 架构决策（用什么技术、怎么分层） | 具体的函数名（还没写，随时会改） |
| 数据模型（核心实体和关系） | 文件的精确组织结构（实现过程中会调整） |
| Phase 顺序（先做什么后做什么） | 每个函数的参数列表（写到那一步再决定） |
| 用户故事的归属（哪个 Phase 实现哪个 Story） | 详细的伪代码实现（那是实现阶段的工作） |

#### **Bad Plan 的典型特征**
- 所有函数名都写死了（`createUser()`，`updateUserProfile()`，`deleteUser()`...）
- 看起来像一份完整的"用户手册"而非"路线图"
- 当 Phase 1 实际编写代码时，这些函数名大概率会变

### 🔄 **六、从 Naive Plan 到 Tracer Bullet Plan 的转变**

#### **转换流程**

```
Naive Plan（LLM 默认输出）
    ↓
1. 重新组织为 Vertical Slices（每个 Phase = 一个完整功能）
    ↓
2. 链接到 PRD User Stories（每个 Phase 明确引用 Story 编号）
    ↓
3. 只保留 Durable Decisions（删除所有函数名、伪代码）
    ↓
Tracer Bullet Plan（可执行的高质量计划）
```

#### **讲师的处理方法**

1. 拿到 LLM 生成的 Plan 后，**手动合并 Phase**（例如从 5 个合并为 3 个）
2. 将 Phase 从水平分层改为 Vertical Slices
3. 删除所有非持久性细节（函数名、伪代码）
4. 每个 Phase 引用 PRD 中的 User Story

> **核心操作**：拿到 LLM 生成的 Plan 后，讲师在 `claude-code.md`（自己做记录的文件，不是 CLAUDE.md）中重写，然后交给 Claude Code 执行。

### 📊 **七、Naive Plan vs Tracer Bullet Plan 完整对比**

| **维度** | **Naive Plan** | **Tracer Bullet Plan** |
|----------|---------------|----------------------|
| **Phase 划分依据** | 技术层（Service / UI / Route） | 用户功能（Story #1 / Story #2） |
| **每个 Phase 的交付物** | 一个技术层的建设 | 一个端到端完整功能 |
| **可验证性** | 最后才能验证 | 每个 Phase 都可验证 |
| **引用 PRD** | 无（LLM 自己发挥） | 明确引用 User Story 编号 |
| **决策类型** | 所有细节（含函数名） | 仅 Durable Decisions |
| **变更成本** | 高（前面决策固化） | 低（每个 Phase 可调整） |
| **人类介入** | 不需要（LLM 全自动） | 需要手动合并和精简 |
| **比喻** | 高层建筑——一层层向上盖 | 种树——每棵树独立生长 |
