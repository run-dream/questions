### 📋 **一、什么时候需要创建 PRD？**

#### **核心判断标准**

| **任务规模** | **是否需要 PRD** | **理由** |
|-------------|-----------------|---------|
| 小功能（修复 Bug、添加简单按钮） | 不需要 | 单个 Smart Zone 可容纳 |
| 中等功能（添加一个完整页面） | 视情况 | 如果需求明确，可直接实现 |
| **大任务（重构、Analytics Dashboard）** | **必须需要** | **溢出上下文窗口，需要拆分** |

#### **PRD 解决的问题**
- 大任务会溢出 LLM 的上下文窗口（Smart Zone 限制）
- 需要将任务"物化"为外部文档，让 AI 在多个会话间保持一致理解
- 将人类的**品味（Taste）**注入 AI 的工作流中

> **讲师的判断标准**："If a task is too big for a single context window, create a PRD."

### 🔄 **二、2PRD Skill 工作流**

2PRD 是将 Grill Me 对话产物转成 PRD 文档的 Skill。

#### **完整的 2PRD 流程**

```
Step 1: /grill-me
  → AI 访谈你，了解需求、约束、偏好
  → 达成 shared design concept（共享设计概念）
  ↓
Step 2: 达成共识后 → /2PRD
  → AI 探索代码库（Explore repo）
  → 使用模板写 PRD 并保存到本地文件
  ↓
Step 3: 审查 PRD
  → 确认 PRD 是否捕获了 shared design concept
  → 修改 PRD（这是人类 impose taste 的关键环节）
  ↓
Step 4: Commit PRD
  → 仅提交文档（PRD 文件），不实现任何代码
  → PRD 进入版本管理系统
```

#### **操作流程表**

| **步骤** | **命令/操作** | **产出** | **注意事项** |
|----------|-------------|---------|-------------|
| 1 | `/grill-me` | 访谈记录 | 不要跳过，这是与 AI 达成共识的关键 |
| 2 | `/2PRD` | PRD 文档文件 | AI 会自动探索代码库 |
| 3 | 审查并修改 | 修改后的 PRD | **这是人类施加品味的地方** |
| 4 | `git add PRD.md && git commit` | 版本化的 PRD | **只提交文档，不写代码** |

### 🏗️ **三、PRD 模板详细结构**

#### **标准模板（三部分核心结构）**

```
PRD.md
├── 1. Problem Statement（问题陈述）
├── 2. Solution（解决方案）
├── 3. User Stories（用户故事）
├── 4. Implementation Decisions（实现决策）
├── 5. Out of Scope（不在此范围）
└── 6. Further Notes（其他说明）
```

#### **1. Problem Statement（问题陈述）**

> **视角**：从用户的视角描述——用户当前面临什么困难/痛点

| **维度** | **好的 Problem Statement** | **差的 Problem Statement** |
|----------|---------------------------|---------------------------|
| **视角** | 用户视角 | 技术视角 |
| **内容** | 用户不能做什么、为什么要做 | 我们要用什么技术栈 |
| **措辞** | "作为讲师，我无法看到学生的完成率趋势" | "系统缺少一个数据分析模块" |
| **目的** | 让所有人都理解"为什么要做这个" | 只是形式化地写一段话 |

#### **2. Solution（解决方案）**

> **视角**：也是从用户的视角描述——用户将如何操作/受益

- **同样保持用户视角**：用户将如何与这个功能交互
- **描述行为而非实现**：用户可以做什么，会看到什么
- **保持具体**：能明确的就明确，模糊的地方留给 User Stories 展开

#### **3. User Stories（用户故事）**

> **格式**：`As a [role], I want [action], so that [reason]`

| **要素** | **解释** | **示例** |
|----------|---------|---------|
| **Role（角色）** | 谁在使用这个功能 | "As a course instructor" |
| **Action（行动）** | 他们想要做什么 | "I want to view student completion rates" |
| **Reason（原因）** | 为什么需要这个功能 | "so that I can identify struggling students" |

**User Story 编号**：每条 User Story 从前到后编号（US-1、US-2、US-3...），Plan 和实现阶段直接引用这些编号。

> **注意**：User Stories 的编号是连接 PRD 和 Plan 的关键桥梁。Plan 中的每个 Phase 都引用具体的 User Story 编号。

#### **4. Implementation Decisions（实现决策）**

- AI 生成的实现建议
- 包含技术选型、关键依赖
- 人类审查并确认

#### **5. Out of Scope（不在此范围）**

> **Out of Scope 的重要性**——它定义了"不做什么"，和"做什么"同样重要

| **作用** | **说明** |
|----------|---------|
| **约束 AI** | 防止 AI 在工作时"擅自加料"（Feature Creep） |
| **保持焦点** | 明确项目边界，避免 Scope Creep |
| **简化决策** | 不需要在实现时纠结"这个要不要做" |
| **评审参考** | 团队成员知道什么是明确排除的 |

**示例**：
```markdown
## Out of Scope
- 移动端适配（此版本不做）
- 用户角色管理（单独项目）
- 数据导出功能（后续版本考虑）
```

#### **6. Further Notes（其他说明）**

- 任何不适合上述分类的补充信息
- 设计约束
- 已知限制
- 团队约定

### 👤 **四、人类品味（Impose Taste）的关键环节**

#### **PRD 是人类 vs AI 的分界线**

| **AI 负责** | **人类负责** |
|------------|-------------|
| 从对话中提取结构化的需求 | 判断"这是不是我想要的" |
| 生成 PRD 模板的初稿 | 调整措辞、补充遗漏 |
| 建议技术实现方案 | 决定"我们真的需要这个功能吗" |
| 识别可能的边缘情况 | 设定优先级（这个 vs 那个，先做谁） |

> **讲师的核心观点**："PRD is where you impose your human taste." — PRD 是你作为人类施加品味的地方。

#### **你不应该让 AI 替你做的决定**
- 产品的核心方向
- 功能的取舍（哪些做、哪些不做）
- 用户故事的优先级排序
- 什么算"足够好"的标准

### 💾 **五、PRD 的版本管理与提交流程**

#### **关键规则**

| **规则** | **说明** |
|----------|---------|
| **仅提交文档** | PRD 确认后只 commit PRD 文件，不写一行代码 |
| **PRD 进入版本控制** | Git 记录 PRD 的变更历史 |
| **PRD 确认后再创建 Plan** | 先有目的地（PRD），再有路线图（Plan） |
| **Plan 确认后再开始实现** | 先有路线图，再出发 |

#### **为什么 Commit PRD 而不实现？**
- 让 PRD 进入版本控制，有清晰的变更记录
- PRD 和实现代码的变更历史分离，便于追溯
- Commit 的 PRD 是"冻结的需求"，Plan 和实现都基于这个冻结版本
- 需求变更时，更新 PRD 再 commit 新的版本

### ⚖️ **六、PRD 模板的灵活性与争议**

#### **讲师的态度**
- 当前的 3 段式（Problem + Solution + User Stories）是**目前的最佳实践**
- 但模板**可以争论和迭代**——这不是圣经
- 如果项目需要更详细的结构，可以扩展（增加 Out of Scope、Implementation Decisions 等）

#### **不同场景的 PRD 调整建议**

| **项目类型** | **PRD 建议** |
|-------------|-------------|
| 单人+AI 快速迭代 | 标准 3 段式就够了 |
| 团队协作（需要评审） | 需要 Out of Scope + Implementation Decisions |
| 探索阶段（需求不明确） | 可能不需要 PRD，先用 Brainstorm |

### 📂 **七、课程中的示例：Instructor Analytics Dashboard**

#### **目标功能**
- 学生数量统计
- 收入统计
- 完成率分析
- 测验得分率分析
- Drop-off 分析（学生在哪一步退出）

#### **为什么用 PRD 工作流？**
- 这个任务"庞大且多变"——功能边界不清晰
- 需求随讨论变化，需要 Grill Me 来收敛
- 适合用 2PRD 工作流逐步收窄需求范围
