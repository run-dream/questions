# Plan 的"做与不做" — Lessons 39-40 & 42-43

> 课程：AI Coding for Real Engineers (Cohort 004)
> 核心概念：Naive Plan vs Good Plan、PRD-to-Plan Skill、Per-Phase 执行、"The proof of the plan is in the pudding"

---

### ⚠️ **一、Naive Plan：大多数人的第一步（也是错误的一步）**

#### **Naive Approach 的典型 Prompt**
```markdown
@PRD → "Turn this into a multi-phase plan."
```

直接将 PRD 丢给 LLM，让它自动生成计划。这是"懒人做法"，通常出现以下问题。

---

### 🔻 **二、Naive Plan 的四大问题**

#### **问题 1：水平分层（Horizontal Layering）**

Naive Plan 几乎总是按技术层划分 Phase：

```markdown
❌ Naive Plan 示例（LLM 自动生成）：

Phase 1: Create Service Layer
  - 实现 UserService、CourseService、AnalyticsService
  - 定义数据模型和 Repository 层

Phase 2: Create UI Components
  - 构建 Dashboard 页面
  - 实现图表组件和表格组件

Phase 3: Create Routes & Navigation
  - 添加路由配置和导航菜单
  - 实现权限控制

Phase 4: Create Admin Panel
  - 构建管理员界面
  - 实现数据筛选和导出
```

| **问题** | **为什么有害** |
|----------|--------------|
| 每个 Phase 只做一个技术层 | 各层之间的假设不匹配，整合时才暴露问题 |
| 到 Phase 4 才能看到完整功能 | Stakeholders 无从验证进度 |
| 前后 Phase 有隐性依赖 | 前期决策错误，后期大面积返工 |

#### **问题 2：过于具体（Too Specific）**

Naive Plan 倾向于把所有函数名都写死：

```markdown
❌ Naive Plan 中的过度具体内容：

Phase 1:
  - 创建 `analyticsService.getCompletionRate()`
  - 创建 `analyticsService.getRevenue()`
  - 创建 `analyticsService.getDropOffRate()`
  - 创建 `analyticsController.handleGetAnalytics()`
  ...
（此处省略 50 个函数签名）
```

| **问题** | **为什么有害** |
|----------|--------------|
| 这些函数名在实现时大概率会变 | 计划变成了"假承诺" |
| 浪费了 LLM 的计算资源 | LLM 花 token 生成可能永远不会用的函数名 |
| 给人一种"计划很详细"的错觉 | 貌似精确但实际不可靠 |

#### **问题 3：没有引用 PRD User Stories**

Naive Plan 通常与 PRD 脱节：

```markdown
❌ Phase 描述中没有 User Story 引用：
  Phase 1: Implement data models
  Phase 2: Build API endpoints

  → AI 不知道每个 Phase 在做哪个 User Story
  → 无法判断一个 Phase 是否完成了某个功能
  → Phase 边界模糊，容易 Scope Creep
```

| **问题** | **为什么有害** |
|----------|--------------|
| 没有用户故事作为 Phase 的"完成标准" | Phase 的边界模糊，什么时候算做完？ |
| AI 不知道自己在实现什么产品价值 | 只堆技术层，忘记产品目标 |
| 各 Phase 之间优先级不清晰 | 先做什么、后做什么没有业务依据 |

#### **问题 4：像用户手册不是路线图**

| **维度** | **用户手册（User Manual）** | **路线图（Roadmap）** |
|----------|---------------------------|---------------------|
| **内容** | 每一步的具体操作 | 目标、方向、关键决策 |
| **粒度** | 逐个函数的详细描述 | Phase 级别的功能描述 |
| **变更适应性** | 差（写死了就不能改） | 好（方向不变，路径可调） |
| **类比** | 组装 IKEA 家具的说明书 | 自驾游的导航路线 |

> **Naive Plan 的问题本质**：它试图预测那些无法预测的细节（函数名、文件路径），而忽略了真正需要计划的内容（架构决策、Phase 顺序、关键约束）。

### ✅ **三、Good Plan：Tracer Bullet + PRD 引用 + Durable Decisions**

#### **讲师的处理流程**

```
1. LLM 生成 Naive Plan（默认输出）
2. 讲师手动审查并重写
    - 合并 Phase（5个→3个）
    - 改为 Vertical Slices
    - 引用 PRD User Stories
    - 删除非持久细节
3. 使用 PRD-to-Plan Skill 辅助生成
4. 最终得到一个 Tracer Bullet Plan
```

#### **Good Plan 示例**

```markdown
✅ Good Plan 示例（经过人类审查和重写）：

Phase 1: Core Dashboard [US-1, US-2]
  - 实现学生数量统计和收入统计的完整功能链路
  - 数据模型 → API → 前端展示（垂直切片）
  - 决策：使用 Chart.js 作为可视化库
  - 不包含：完成率分析（Phase 2）

Phase 2: Performance Analytics [US-3, US-4]
  - 实现完成率分析和测验得分率分析
  - 复用 Phase 1 的数据模型和 API 模式（决策已稳定）
  - 决策：完成率使用堆积柱状图展示
  - 不包含：Drop-off 分析（Phase 3）

Phase 3: Drop-off & Reporting [US-5]
  - 实现 Drop-off 分析（学生在哪一步退出）
  - 构建 PDF/CSV 导出功能
  - 聚合所有数据分析结果
```

#### **Good Plan 的五个特征**

| **特征** | **说明** | **Good Plan 示例** |
|----------|---------|-------------------|
| **1. 3 个 Phase（而非 5+）** | 讲师手动合并，避免碎片化 | 5 个 Phase → 合并为 3 个 |
| **2. 垂直切片（Vertical Slices）** | 每个 Phase 贯穿全栈 | "实现完整功能链路"而非"只做 Service 层" |
| **3. 引用 PRD User Stories** | 引用编号，明确 Phase 负责的内容 | `[US-1, US-2]` |
| **4. 仅 Durable Decisions** | 写架构决策而非伪代码 | "使用 Chart.js"而非"getChartData()" |
| **5. 描述而非伪代码** | 用自然语言描述"做什么"而非"怎么写" | "实现学生数量统计"而非"创建 StudentCount 组件" |

### 🔄 **四、PRD-to-Plan Skill 的正确使用方式**

#### **推荐 Prompt**

不要用 `@PRD → "Turn this into a multi-phase plan"`，而是使用**专门为 Plan 设计的 Skill**（如 PRD-to-Plan Skill），并在 prompt 中明确要求 Tracer Bullets 和 Vertical Slices。

#### **协作流程**

```markdown
Step 1: /grill-me → 访谈需求
Step 2: /2PRD → 生成 PRD 文件
Step 3: @PRD → PRD-to-Plan Skill → 生成 Plan
Step 4: 人类审查 Plan → 重写为 Tracer Bullet Plan
Step 5: Commit Plan（与 PRD 一起版本化）
Step 6: 执行 Phase 1 → 验证 → 调整 Plan → 执行 Phase 2 → ...
```

### 🚀 **五、Per-Phase 执行工作流**

#### **每个 Phase 的 Prompt 结构**

```markdown
@PRD @Plan → Do Phase N
```

每次执行一个 Phase 时，都要同时传入**完整的 PRD** 和**完整的 Plan**。

#### **为什么每次都要传完整 Plan？**

| **做法** | **结果** |
|----------|---------|
| 只传当前 Phase | AI 不知道其他 Phase 的边界，可能超前实现后面的功能，造成代码冲突 |
| 传完整 Plan | AI 知道"Phase 3 才做这个"，不会在 Phase 1 提前做 |
| 只传 PRD | AI 没有 Phase 边界，可能自由发挥，偏离计划 |

> **示例**：Phase 2 做数据采集，Phase 3 做数据可视化。如果不传完整 Plan，Phase 2 的 AI 可能自作主张开始画图，导致重复工作或代码冲突。

#### **Phase 执行流程**

```markdown
1. /clear → 清空上下文（保持 Smart Zone）
2. 加载 PRD + Plan 到新会话中
3. Prompt: @PRD @Plan → Do Phase N
4. AI 执行 Phase N
5. 验证 → 如果发现问题，修复或 Handoff
6. Commit 当前 Phase 的代码
7. /clear → 进入下一个 Phase
```

#### **关键规则**

| **规则** | **说明** |
|----------|---------|
| **每个 Phase 独立会话** | 每完成一个 Phase 就 `/clear`，下一个 Phase 开新会话 |
| **每个 Phase 完成后 Commit** | 提交代码，进入版本控制 |

### 📊 **六、Naive Plan vs Good Plan 完整对比**

| **维度** | **Naive Plan** | **Good Plan (Tracer Bullet)** |
|----------|---------------|-------------------------------|
| **生成方式** | LLM 自动（一次 Prompt） | 人类审查 + 重写 |
| **Phase 数量** | 5+（LLM 默认倾向） | 3（人类手动合并） |
| **Phase 结构** | 水平分层 | 垂直切片 |
| **PRD 引用** | 无 | 明确引用 User Story 编号 |
| **内容粒度** | 函数名、伪代码 | 仅 Durable Decisions |
| **写作风格** | 像用户手册 | 像路线图 |
| **变更适应性** | 差（细节写死） | 好（方向明确，路径灵活） |
| **可验证性** | 最后才能验证 | 每个 Phase 可验证 |
| **人类投入** | 低（全交给 LLM） | 中（审查 + 重组） |

### 🧪 **七、最终原则："The Proof of the Plan is in the Pudding"**

> **"The proof of the plan is in the pudding."** — 讲师的核心态度

| **含义** | **实践** |
|----------|---------|
| 计划好不意味着能执行好 | 每个 Phase 执行后验证，再调整后续 Phase |
| 计划必须接受现实的检验 | 执行中发现计划不合理，就修改计划 |
| 执行力比计划完美度更重要 | 3 个粗糙的 Phase 执行完，比 5 个精心设计的 Phase 没做完强 |

#### **实践检查清单**

每个 Phase 执行完，问自己：
1. 这个 Phase 的功能端到端可用吗？（垂直切片验证）
2. 代码是否符合 PRD 中的用户故事？（需求验证）
3. 是否需要调整后续 Phase 的 Plan？（计划调整）
4. 发现了什么"计划中没想到的"？（经验积累）
