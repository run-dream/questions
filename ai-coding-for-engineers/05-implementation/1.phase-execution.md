### 🚀 **一、Phase 执行工作流**

#### **每 Phase 执行的 Prompt 结构**

```
@PRD @Plan → Do Phase N
```

每次执行一个 Phase 时，同时传入**完整 PRD** + **完整 Plan**。

| **要素** | **为什么需要** |
|----------|--------------|
| **完整 PRD** | AI 知道"最终要建成什么样" |
| **完整 Plan** | AI 知道"Phase 3 才做这个，我现在不做" |

#### **执行流程**

```markdown
1. /clear → 清空上一个 Phase 的上下文
2. 加载 PRD + Plan 到新会话
3. Prompt: @PRD @Plan → 执行 Phase N
4. AI 完成 Phase N 的实现
5. 手动验证代码质量
6. 如发现 → Bug 修复（参见下文）
7. Commit Phase N 的代码
8. /clear → 进入 Phase N+1
```

---

### 🐛 **二、执行中发现的 Bug 处理**

#### **发现 Bug 的典型场景**

在 Phase 执行过程中，AI 或人类可能发现：

| **Bug 类型** | **示例** | **处理方式** |
|-------------|---------|-------------|
| **当前 Phase 的 Bug** | 刚写的代码逻辑错误 | 在当前会话修复 |
| **之前 Phase 的 Bug** | Phase 1 的数据模型有问题 | Handoff 到新会话修复 |
| **依赖库 Bug** | 第三方库的已知问题 | 寻找替代方案 |
| **环境 Bug** | 配置错误导致 CI 失败 | 调整配置 |

#### **修复之前 Phase 的 Bug**

如果不影响当前 Phase 的边界，可以用 **Handoff 机制**：

```
当前 Phase 执行中发现 Phase 1 的 Bug
    ↓
撰写 Handoff 文档，描述 Bug 和修复方案
    ↓
启动新会话，读取 Handoff 文档
    ↓
在新会话中修复 Bug
    ↓
提交修复 → 回到当前 Phase
```

### ✅ **三、QA 策略**

| **QA 方式** | **说明** | **时机** |
|-----------|---------|---------|
| **手动验证** | 运行代码、检查 UI、测试功能 | 每个 Phase 完成后 |
| **AI Code Review** | 让 AI 审查代码质量 | 每次 Commit 前 |
| **测试执行** | 运行现有测试套件 | 每次修改后 |
| **端到端验证** | 验证完整功能链路 | 整个项目完成后 |

---

### 🔧 **四、每个 Phase 的 Commit 策略**

| **规则** | **说明** |
|----------|---------|
| **每个 Phase 完成后 Commit** | Phase 完整交付后再提交 |
| **Commit 前验证** | 保证 Phase 功能端到端可用 |
| **Commit 后 /clear** | 清空上下文，为下一 Phase 做准备 |
| **保持小粒度 Commit** | 每个 Commit 包含一个 Phase 的完整变更 |
